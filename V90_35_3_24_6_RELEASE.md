# HUD Controller v90.35.3.24.6 + U2W v8.25 — validated-GOP recovery

This is a **paired iOS app + U2W firmware release**. Unlike v90.35.3.24.5, the adapter must be updated to **v8.25** to exercise the intended recovery behavior.

## Why this iteration

The 2026-09-21 evening road test separated two failure layers:

- The iPhone/HUD composite continued rendering navigation overlays after the CarPlay background map stopped advancing at MainVideo frame 5481.
- The stable v8.11 exporter remained alive and eventually reported many additional IDRs, while v8.24 could spend long periods without a usable recent in-memory anchor.
- v90.35.3.24.5 successfully eliminated the old rapid decoder-reconnect storm, but an iPhone reconnect could still wait too long for a clean SPS/PPS/IDR bootstrap.

## U2W v8.25

v8.25 keeps the v8.11 capture path unchanged and replaces the fragile recent-anchor spool with a validated rolling-file GOP rescan at recovery boundaries.

- Scan the current bounded v8.11 rolling file on new/recovered client connection.
- Locate the newest validated 800×480 SPS/PPS/IDR GOP.
- Replay only that newest GOP, with a 48 MiB cap, directly from disk and with 4 ms-per-frame pacing, then continue at the live edge. The cap is a safety bound, not a RAM allocation.
- Re-seed after v8.11 source-generation rotations.
- Fall back to the next validated live IDR if no bounded valid GOP is available.
- Preserve dedicated TCP/15332 transport; no long-lived H.264 video through Boa.

AppleCarPlay, Route Guidance, Now Playing, and the stable HUD JPEG relay v8.15.1 are deliberately untouched.

### Offline capture validation

The same H.264 validator was run against a previously collected **37,201,056-byte** full v8.11 rolling capture. It selected the genuine decoder-safe GOP, rejected **517** malformed/false Annex-B candidates, and produced a **36,660,827-byte / 5,168-frame** clean replay. `ffprobe` decoded all 5,168 frames at **800×480 with zero error lines**. This capture also demonstrated that an 8 MiB cap would be too small, so the final safety bound is 48 MiB with disk streaming and 4 ms-per-frame catch-up pacing.

## iOS app changes

- Recognizes v8.24 and v8.25 relay status during transition/rollback.
- Shows v8.25 file-GOP scan, bootstrap, cap-rejection, generation-reseed, and rejected-NAL diagnostics.
- Keeps the v90.35.3.24.5 bounded decoder policy: one recovery reseed per stall episode, then preserve TCP and wait for a genuinely new live IDR if that bootstrap immediately fails.
- Recovery wording and diagnostics now distinguish validated-GOP recovery from the older v8.24 recent-anchor path.

## FPS and OBD probes

The existing 5/8/10/12/15 FPS HUD probe remains. Because the 15 FPS drive produced a separate physical-HUD MJPEG session failure while the iPhone renderer remained active, **10 FPS is recommended for the first v8.25 road test**. This does not prove 15 FPS caused the viewer failure.

OBD speed probe v2 remains diagnostic-only. The last test confirmed PID 0x0D is advertised but found no phone-facing HUD field that tracks actual speed, so GPS remains the production speed source.

## Ambient behavior

No new Door-light reconciliation/reassert logic was added in this release. The user elected to observe the prior physical-brightness mismatch again before changing ambient behavior.

## Test sequence

1. Flash `u2w/v8.25_ValidatedGOPRecovery/U2W_Update_v8.25_ValidatedGOPRecovery.img` while connected to the U2W Wi-Fi.
2. Install/build the paired v90.35.3.24.6 app.
3. Parked preflight: verify MainVideo reaches `LIVE` and frames advance continuously for at least 20 seconds.
4. For the first drive, select **10 FPS**.
5. After the drive, collect the HUD log plus U2W video/relay/HUD status if any map or physical-HUD freeze occurs.
