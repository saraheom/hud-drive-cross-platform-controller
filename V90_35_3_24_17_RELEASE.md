# HUD Controller v90.35.3.24.17 — MainVideo reference-continuity recovery

**Pair:** existing **U2W v8.31 Navigation-Priority Raw MainVideo**. This is an **app-only** update; do **not** reflash the adapter.

## What the 2026-10-01 one-drive diagnostic proved

The v24.16 recorder separated the source from the decoder failure:

- MainVideo decoded normally after startup, including after the initial reverse-camera transition.
- The last sustained successful iPhone decode output was around **12:58:49Z** (08:58:49 EDT).
- Raw TCP/15332 H.264 bytes continued arriving until the app was intentionally background-stopped around **13:01:06Z**.
- During that interval VideoToolbox accumulated **4,111 output-callback `codecBadDataErr (-8969)` failures** while the transport remained live.
- The independent passive U2W observer continued seeing the exact v8.11 mirror for the rest of the drive, ultimately recording hundreds of MiB of source data and tens of thousands of valid access units. `AppleCarPlay` and the v8.11 exporter therefore did **not** stop at MLK Drive.
- The passive observer explicitly recorded **`frame_num` discontinuities** and source-generation changes. The old iPhone sanitizer already parsed `frame_num`, but did not enforce continuity; syntactically plausible dependent P-slices could therefore enter VideoToolbox after a missing reference picture.

This makes the primary failure a **reference-chain continuity/recovery bug on the iPhone side of the v8.31 raw relay**, not a CarPlay-navigation or route-guidance outage.

## Fix 1 — reject a broken H.264 reference chain before VideoToolbox

`H264MainVideoSanitizer` now tracks the first slice of each reference picture using the validated SPS `MaxFrameNum` modulus.

For reference P-pictures, the expected next value is:

`expected_frame_num = (previous_frame_num + 1) mod MaxFrameNum`

If the raw v8.11 stream jumps across a missing reference picture:

1. the discontinuous P-slice is rejected;
2. dependent P-slices are quarantined;
3. the current VideoToolbox reference state is invalidated immediately;
4. the last validated SPS/PPS pair is preserved; and
5. decode resumes only at a validated live IDR.

IDRs explicitly reset the continuity gate. A new SPS or a transport reconnect also requires an IDR before dependent slices are admitted.

This is intentionally earlier than the old stale-frame watchdog: the decoder never needs to ingest hundreds or thousands of predictively coded pictures whose reference chain is already known to be incomplete.

## Fix 2 — `-8969` can no longer fail indefinitely

The field drive showed that the old policy was too conservative. After three VideoToolbox `codecBadDataErr (-8969)` failures, it merely armed an atomic rebuild for some later IDR while continuing to feed the poisoned epoch. That produced thousands of callback failures.

v24.17 changes both compressed-AU and output-callback handling:

- one or two isolated `-8969` failures are still tolerated;
- **three consecutive `-8969` failures request bounded hard recovery**;
- the existing source-epoch quarantine path clears stale sanitizer/decoder parameter-set state;
- the healthy TCP/15332 connection is preserved; and
- recovery waits for a complete fresh **SPS → PPS → IDR** codec epoch.

`kVTInvalidSessionErr (-12903)` retains its existing hard-recovery handling.

## Fix 3 — do not intentionally kill a healthy live-map session on background

v24.16 explicitly stopped app-only preview and restored Navigation when SwiftUI entered background. The diagnostic drive therefore stopped its iPhone MainVideo connection at ~13:01 even though the adapter source remained healthy afterward.

v24.17 no longer performs that proactive teardown. Active preview/Map Mode keeps its decoder/TCP/HUD-cast state across a background transition. The app's existing background location/BLE work remains responsible for scheduling; if iOS actually suspends execution, the existing source/output watchdogs handle the real gap when execution resumes.

This change does not make ordinary Navigation start MainVideo: v8.31 remains **explicit/on-demand only**.

## Safety boundary retained

Unchanged from v24.16/v8.31:

- exact v8.11 AppleCarPlay exporter;
- existing v8.8 Route Guidance / Now Playing path;
- no `AppleCarPlay` kill, signal, restart, or injection;
- no adapter-side H.264 parser/cache/reference-chain spool;
- no MainVideo autostart in ordinary Navigation;
- physical HUD mode 6 is entered only after a real decoded live frame;
- diagnostic recorder and parked one-tap ZIP remain available.

## First validation drive

1. Install v90.35.3.24.17.
2. Keep the currently installed **U2W v8.31**; do not reflash.
3. Start the car/CarPlay normally and start Google Maps navigation.
4. Enable Map Mode normally. **10 fps** remains the preferred first validation cadence.
5. No manual Live Preview is required for the fix test unless you specifically want to watch the app preview before enabling physical Map Mode.
6. Leave the app running normally; it is now allowed to remain live if it backgrounds.
7. If the image freezes at all, leave the route running. After parking, tap **Collect Live Map Diagnostic ZIP (parked)** once. The retained v24.16 recorder will show whether the new continuity gate recovered at the next IDR/fresh codec epoch.
