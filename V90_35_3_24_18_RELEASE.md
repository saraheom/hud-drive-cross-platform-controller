# HUD Controller v90.35.3.24.18 — Robust Map Mode + MainVideo Next-IDR Recovery

Pair with the existing **U2W v8.31 Navigation-Priority Raw MainVideo** image. No adapter reflash is required.

## Why this build exists

The 2026-10-01 field drive isolated two independent failures:

1. **Physical Map Mode enable failure:** the HUD eventually joined the U2W AP and opened the MJPEG viewer, but the iPhone TCP/15331 JPEG ingress never reached ready, so U2W remained `waiting-first-live-frame` with zero JPEG bytes.
2. **Live MainVideo decoder failure:** raw H.264 bytes and the v8.11 exporter remained healthy while VideoToolbox repeatedly returned `codecBadDataErr (-8969)`. The same drive also proved that rebuilding the iPhone decoder at a later IDR restored live output without changing U2W.

v24.18 fixes both paths while keeping them independent.

## Physical Map Mode — restored fallback-first behavior

The physical HUD no longer waits for MainVideo to decode before Map Mode can start.

Startup is now:

1. Start the existing U2W HUD JPEG relay.
2. Start TCP/15331 iPhone -> U2W frame ingress.
3. Render the 480x240 Map Mode canvas immediately.
   - Fresh MainVideo available: use the live CarPlay map image.
   - MainVideo unavailable/stale/recovering: use the existing schematic fallback map.
4. Require one JPEG to be successfully accepted by U2W.
5. Run the field-proven HUD sequence: **mode 6 once -> STA credentials once -> wait**.

A MainVideo decoder failure therefore no longer forces physical Map Mode to exit.

## TCP/15331 hardening

The 2026-10-01 drive exposed a Network.framework state where the connection never reached `.ready` or `.failed`.

v24.18 adds:

- explicit `.setup`, `.preparing`, and `.waiting` handling;
- a 2.5 s connect deadline;
- bounded TCP/15331 recreation if it never becomes ready;
- a deterministic `ensureConnection` checkpoint when the HUD reports STA/DHCP link-up;
- first-JPEG verification before the HUD is handed to mode 6.

The adapter-side v8.15.1 HUD relay protocol is unchanged.

## MainVideo — preserve SPS/PPS, reset VideoToolbox, resume at next IDR

Repeated `codecBadDataErr (-8969)` no longer leaves the decoder poisoned while thousands of dependent P-frames continue to arrive.

After three consecutive `-8969` failures:

- keep U2W v8.31 TCP/15332 alive;
- preserve the last validated SPS/PPS pair;
- invalidate VideoToolbox;
- quarantine reference-picture continuity / reject dependent P-frames;
- wait for the next validated IDR;
- rebuild/decode from that IDR and resume live output.

If a real H.264 `frame_num` reference discontinuity is detected first, the same IDR quarantine/recovery boundary is used.

This matches the field evidence better than requiring a completely new SPS -> PPS -> IDR epoch, because SPS/PPS are not guaranteed to repeat before every IDR.

## Safety / unchanged components

- U2W v8.31 unchanged.
- v8.11 AppleCarPlay MainVideo exporter unchanged.
- Route Guidance / Now Playing paths unchanged.
- AppleCarPlay is never killed, signaled, or restarted by this recovery.
- Ambient-light production modules unchanged.
- HUD BLE transport module unchanged.
- Map Mode canvas/layout module unchanged.
- Existing physical Navigation reassert after HUD reboot remains.
- Existing one-drive diagnostic ZIP remains available if another field failure occurs.

## First validation drive

- Keep U2W v8.31 installed; do not flash a new image.
- Use normal startup order; no reverse-camera or plug-order trick should be required.
- Start Google Maps navigation and enable Map Mode normally.
- 10 fps is a good first validation setting.
- If MainVideo briefly needs recovery, Map Mode should stay on the HUD using the fallback schematic, then return to the live map automatically after the next valid IDR.
- If anything still freezes, do not toggle/restart it during the failure; after parking collect one Live Map Diagnostic ZIP.
