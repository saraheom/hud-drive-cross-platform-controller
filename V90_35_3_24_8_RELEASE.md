# v90.35.3.24.8 + U2W v8.27 — lightweight live-edge MainVideo + HUD diagnostic ZIP reconstruction

This is a deliberately narrow paired release based on the 2026-09-23 field run. It addresses the MainVideo/U2W failure path and the next HUD-native OBD investigation only. **Ambient-light behavior, including the Door overspeed animation/restore sequence, is unchanged.**

## Why v8.27 replaces v8.26

The field run showed that v8.26 could bootstrap correctly but later stop delivering H.264 for repeated ~15-second intervals while the relay process remained present. Reconnecting temporarily recovered the stream. The v8.26 persistent GOP cache also grew close to its 48 MiB cap on the resource-constrained adapter. v8.27 therefore removes the large recovery cache and historical GOP replay rather than trying to tune it again.

## U2W v8.27 MainVideo architecture

The proven v8.11 AppleCarPlay mirror remains the capture source and is not modified:

`AppleCarPlay -> v8.11 /tmp/u2w_mainvideo_live.h264 -> v8.27 TCP/15332 -> iPhone`

v8.27:

- uses wire magic `U2WH2645` with `[u32BE length][NAL]` framing;
- reserves `length=0` as a transport heartbeat while intentionally waiting for a usable live IDR;
- starts at the current live edge and performs no historical full-file/GOP scan;
- creates no persistent GOP cache and deletes the old v8.26 cache on install;
- keeps only bounded parser state plus the latest validated SPS/PPS in memory;
- preserves SPS/PPS/parser state across ordinary v8.11 rolling-file rotation unless the codec parameters really change;
- boots a new/recovering client only on the next validated live IDR;
- drops pre-IDR interframes instead of replaying a large historical GOP;
- keeps the source file descriptor open at EOF and reopens only about every 200 ms to detect v8.11 rotation, avoiding a high-rate open/close loop;
- gives each client a one-second socket send timeout so a blocked/slow iPhone cannot indefinitely stall the relay;
- keeps Boa/CGI outside the long-lived H.264 data path;
- never patches, restarts, or opens internal AppleCarPlay file descriptors.

The installer only replaces the custom MainVideo relay and its start/status CGI files. v8.11 MainVideo capture and v8.15.1 HUD JPEG relay are preserved.

## iOS MainVideo behavior

v90.35.3.24.8 recognizes `U2WH2645` and treats v8.27's `WAITING_LIVE_IDR` / `WAITING_FRESH_IDR` as synchronization states rather than dead transport states.

- Zero-length relay heartbeats keep the TCP session alive while no decodable IDR is available.
- The app does not intentionally reconnect a healthy v8.27 TCP session merely because it is waiting for an IDR.
- A VideoToolbox hard reset on v8.27 preserves TCP and waits for the next clean live IDR; no persistent-GOP replay is requested.
- Startup decoder hysteresis remains: the early decoder is given 8 seconds / 10 decoded frames before the normal 3-second stale-output recovery becomes authoritative.
- Healthy relay CGI polling is reduced to once per 60 seconds for v8.27. TCP is the primary transport; CGI is diagnostic/bootstrapping rather than the hot video path.

## Physical HUD Map Mode fail-safe

A separate field failure showed the iPhone renderer continuing while the physical HUD STA/viewer stopped updating. After a current v8.15.1 display session has genuinely accepted a HUD client and sent a live frame, the app now monitors the HUD's own STA status over the existing HUD BLE protocol.

- Two consecutive no-link/no-address STA results, or no STA status response for more than 12 seconds, are treated as a physical viewer failure.
- A stale physical Map Mode is immediately failed safe to the stock dashboard rather than leaving a frozen image displayed.
- Recovery is bounded to two viewer rebuilds per Map Mode session.
- Viewer recovery restarts only the v8.15.1 HUD display session / HUD STA join. It intentionally keeps MainVideo and the iPhone JPEG renderer alive.
- The existing Route Guidance source gets a 12-second decoded-inactive confirmation window so the observed short Google Maps state-0 hole does not make a Map Mode failure incorrectly restore Freeride.

## HUD OBD diagnostic archive reconstruction

The v4 road probe remains available, but the next investigation now focuses on reconstructing the HUD's own diagnostic archive. The prior capture showed structurally valid `LOG_CATEGORY_CRUSH` chunks even though `LOG_CATEGORY_OBD` was requested, with a 64,360-byte / 1,006-chunk transfer and ZIP/PK content.

v90.35.3.24.8 hardens that transport:

- every STX-bearing diagnostic notification is preserved; repeated archive chunks have nearly identical first BLE notifications and must not be globally de-duplicated;
- a fresh diagnostic STX replaces an incomplete diagnostic wire frame rather than being spliced into it;
- only short-window duplicate continuation notifications inside the current frame are suppressed, while the bounded raw BLE capture still retains every notification;
- normal HUD events interleaved between diagnostic continuation notifications remain routed through the ordinary HUD parser;
- each completed diagnostic chunk must have a plausible category/header and **exactly** its declared payload length;
- the first structurally valid returned archive shape is locked even when the HUD labels it `LOG_CATEGORY_CRUSH` instead of the requested `LOG_CATEGORY_OBD`;
- chunks are stored by their transmitted index, identical duplicates are harmless, conflicting duplicates are reported, and final output is assembled only when every expected index exists;
- assembled byte length is verified against the declared archive size;
- a reconstructed payload beginning with `PK` is saved as a ZIP for offline inspection;
- parked collection is now actually gated to <=1 mph so the heavy diagnostic transfer is not started while driving.

The investigation target after reconstruction is the HUD-side OBD implementation: `010D`, `41 0D` / `410D`, ELM/AT traffic, stock speed values, or service/native traces. The app still does not open a competing second iPhone-to-OBD connection.

## First validation

1. Flash U2W v8.27 while parked; reconnect to the adapter after installation.
2. Verify `u2wvideo-relay-status.cgi` reports `relay_version=v8.27-live-edge-idr`, `wire_magic=U2WH2645`, and `gop_cache_file_bytes=0`.
3. Verify `u2wvideo-status.cgi` still reports `exporter_version=v8.11-mainvideo-live`.
4. Install v90.35.3.24.8.
5. Use 10 FPS for the first validation.
6. While parked, start CarPlay navigation and wait for `LIVE • 20s continuity verified`.
7. Let the system run parked for several minutes if practical, then drive normally. No special power-up order is intended or required.
8. For OBD, run the 90-second HUD-internal road probe if desired. At destination and stationary, tap **Collect/reconstruct HUD OBD ZIP (parked)** and share the reconstructed archive/raw capture if produced.

Field validation is still required. This build is designed to remove the two highest-risk v8.26 mechanisms (large persistent cache and replay/catch-up) rather than claiming that untested firmware can be proven crash-free in advance.
