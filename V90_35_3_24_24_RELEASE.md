# HUD Controller v90.35.3.24.24 + U2W v8.36 Passive Seam Observer

## Purpose

This is a focused evidence + OBD-production release based on the October 5 v24.23/v8.35 field drive. It does **not** introduce another speculative MainVideo recovery algorithm.

### MainVideo

The October 5 drive established two separate facts:

1. U2W v8.35 did invoke its keyframe helper, but the helper returned `send_failed / route=none`. Offline inspection of the captured adapter topology showed that `/var/run/adb-driver` and `/var/run/phonemirror` are Unix **SOCK_STREAM** listeners, while the v8.35 helper used a one-shot **SOCK_DGRAM** sender. v24.24 therefore stops invoking that known-invalid injection route while v8.36 is installed. The exact stock stream handshake/framing remains an offline reverse-engineering task.
2. The 18:04:13 `-8969 codecBadDataErr` failure correlated with a v8.34 mirror generation transition while AppleCarPlay/Route Guidance remained alive. U2W v8.36 adds a passive generation-seam observer so the next evidence bundle can determine whether the unchanged v8.31 relay skips, duplicates, or otherwise mishandles bytes at an inode swap.

### U2W v8.36 safety boundary

v8.36 is a sidecar diagnostic layer over the already-installed v8.35/v8.34/v8.31 stack.

It does **not** replace:

- v8.34 hard-bounded mirror (`SHA-1 b982322ee65fd45405ab40f98512dbd76450976b`)
- exact v8.31 raw relay (`SHA-1 b3964792342f9bc5ad22eaeb70eaf84ec04562f6`)
- v8.35 keyframe helper (`SHA-1 78859319b5cda7f8c42e7026b6f8502b3f7026f1`)

It installs only:

- passive `/tmp/u2w_mainvideo_live.h264` generation observer
- relay start/status wrappers that start/report the observer
- `u2wvideo-seam-log.cgi` for parked evidence collection

The observer never opens TCP/15332, never writes the H.264 mirror, and never signals/restarts AppleCarPlay, ARMiPhoneIAP2, or the raw relay. At each inode generation change it records old/new inode and size, the relay's visible file descriptor/offset/inode/size, SHA-1 and 64-byte boundary samples, plus a passive `/proc/net/unix` and process-socket snapshot.

The normal Live Map diagnostic collection now automatically downloads this seam log.

## Direct ELM327 Map Mode speed

The October 5 parked test proved the OBDII adapter is effectively single-client:

- while HUD owned OBDII, it was unavailable to the iPhone scan;
- after HUD disconnect, `OBDII` immediately advertised service `FFF0`;
- the iPhone connected and received a valid standard `41 0D 00` vehicle-speed response to `01 0D`.

v24.24 therefore implements automatic mode ownership:

- **Entering physical Map Mode:** suspend HUD OBD retry/health ownership, send the stock HUD disconnect, retrieve/connect the remembered OBDII peripheral (or bounded-scan for it), then poll only `01 0D` at 5 Hz.
- **While Map Mode is active:** fresh OBD speed is primary; GPS is fallback if the direct sample is absent/stale.
- **Leaving Map Mode for Navigation/Freeride:** stop polling, disconnect the iPhone from ELM327, then return OBD ownership to the HUD and resume the user's normal auto-connect policy.

No `ATZ`, `ATSP0`, adapter reset, or protocol-selection command is sent.

## Map Mode Speed Warning card

A separate compact **Map Mode Speed Warning** card is placed immediately below the main Custom Map Mode block on the Navigation tab. It is intentionally separate from Map Mode diagnostics and image customization.

Persistent controls:

- Enable/disable overspeed warning
- Independently enable/disable speed-number color change
- Choose speed-number warning color
- Independently enable/disable speed-background highlight
- Choose background warning color
- Background opacity

The warning compares the Map Mode displayed speed (fresh OBD first, GPS fallback) against the active posted speed limit. Navigation and Freeride retain their stock HUD speed behavior.
